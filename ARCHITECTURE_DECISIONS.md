# Архитектурные решения TradeDiary

Живой журнал решений по архитектуре продукта. Компаньон к однократному
`ARCHITECTURE_REVIEW.md` (там — снимок на дату ревью, здесь — эволюция).

**Как дополнять:** новая запись сверху, формат — «решение / контекст /
рациональное / что НЕ делаем», с датой. Коротко, на русском, без кода.

## 17.09.2026 — Журнал идей (run-log) для будущей аналитики

**Решение:** append-only SQLite-журнал `idea_log.db` (схема v1, `PRAGMA
user_version`) с авто-записью каждой идеи: при открытии сделки — входные данные
+ технический снимок НА ДАТУ ВХОДА, при закрытии — исход. Данные накапливаются
сейчас, отображение/аналитика — потом.

**Контекст:** статистика прогонов нужна для анализа эффективности, но нет ни
времени, ни потребности строить аналитику прямо сейчас; главное — не потерять
данные и не получить look-ahead bias.

**Рациональное:**
- Схема фиксирована и версионируется (PRAGMA user_version=1) — миграция без
  боли, когда данных накопится.
- Технический снимок (SMA200/MACD/RSI/статус) пишется один раз на дату сигнала
  и НЕ пересчитывается при закрытии/в будущем — иначе бэктест окажется искажён.
- Фундаментальный снимок берётся из существующего кэша `company_metrics`
  (без сети на UI-потоке).
- Повторный лог той же идеи обновляет снимки по ключу (ticker, entry_date,
  entry_price, direction), дубликатов нет; закрытые записи не трогаются.
- Вероятность/главный риск/источник (из отчёта Perplexity) — аннотация
  (`annotate_idea_by_ticker`), т.к. программа их не вычисляет.

### Что НЕ делаем
| Идея | Решение | Почему |
|---|---|---|
| Удаление/очистка журнала | Никогда | История не должна теряться |
| Пересчёт технического снимка при анализе | Не делаем | Look-ahead bias |
| Сеть/пересчёт на UI-потоке при записи | Не делаем | Только чтение кэшей + локальная SQLite |
| UI для отображения/аналитики журнала сейчас | Отложено | Данные копятся, отображение потом |

## 17.09.2026 — Simple Mode: Technical timing (Watchlist + DealDialog)

**Решение:** единая система из двух мест — Watchlist отвечает «стоит ли смотреть
на вход?», DealDialog отвечает «какой риск я принимаю?». Watchlist считает
тех. статус (колонка Tech / диалог Technical timing), DealDialog показывает
только последний рассчитанный результат из БД (без повторного анализа).
Подробно о намерении: рекомендации «Ready to consider entry — не Buy now».

**Контекст:** Simple Mode; статус нужен как «нет сильного технического
конфликта», а не как «идеальный вход».

**Рациональное:**
- 3 статуса (READY TO CONSIDER ENTRY / WAIT / REASSESS) по числу конфликтов со
  стороной идеи (long: цена<SMA200 / death cross / MACD bearish; short — зеркально).
- RSI/растянутость НЕ блокируют вход: при READY это только мягкое предупреждение
  (жёлтая строка + подсказка козы), чтобы не создавать бота, ждущего идеальное дно.
- Хранение — отдельный SQLite `technical_timing.db` (kv, TTL 24ч); цены из
  `price_history.db`, пересчёт строго в фоновом потоке (`_TechnicalTimingThread`).
- Watchlist по умолчанию считает long (направление идеи в записи не хранится);
  DealDialog берёт своё реальное направление (BUY/SELL) с fallback на любой.

### Что НЕ делаем

| Идея | Решение | Почему |
|---|---|---|
| Статус «Ready with caution» (catalyst + смешанная техника) | Убрать | Остаются ровно 3 статуса; catalyst виден отдельно в колонке Catalyst |
| Влияние катализатора на тех. статус | Не делаем | Катализатор уже в колонке Catalyst / Simple-карточке; не перегружаем правила |
| Требование «все индикаторы bullish» для Ready | Не делаем | Вечный Wait и опоздание входа |
| Авто-SL/TP из индикаторов в DealDialog | Не делаем | Индикаторы — контекст; стоп выбирает пользователь, программа только считает риск |
| Паттерны (breakout/pullback), уровни S/R, уведомления о смене статуса | Отложено (Этап 3) | Не появятся без реальной потребности; уведомления создают шум |
| Новый расчёт внутри DealDialog | Не делаем | DealDialog берёт результат уже рассчитанного Watchlist monitor |

## 17.09.2026 — Simple Mode: portfolio construction / risk management

### Что НЕ добавляем / не делаем

| Идея | Решение | Почему |
|---|---|---|
| Auto-sizing из корреляции портфеля | Не делать | Ложная точность и смешение риска портфеля с логикой стопа по одной акции |
| Автоматически менять SL/TP по macro/regime | Не делать | SL/TP должны следовать тезису и структуре сделки, а не индикатору общего рынка |
| Авто-ребалансировка | Не делать | Слишком много скрытых допущений и лишнего контроля над решением пользователя |
| Автоматический MLRCI backtest | Не приоритет | Сначала определить, влияет ли MLRCI на реальные решения |
| ROA / ROE в Simple Mode | Не добавлять | Дублируют ROIC и усложняют interpretation |
| Новые макро-индикаторы | Не добавлять | Macro score, regime и late cycle уже полностью закрывают роль контекста |
| Корреляционный heatmap в основном потоке | Спрятать в Details | Полезна для исследования, но не нужна на каждом решении |
| Фейковая история сделок | Убрать из пользовательской аналитики | Она создаёт видимость доказательности и может исказить выводы о собственной статистике |
| Equity/portfolio beta, volatility, VaR, ES, Sharpe/Sortino, covariance, optimal weights, efficient frontier, risk parity | Не добавлять в Simple Mode | Не дают простого действия «что делать дальше»; статистика «для красоты» запрещена |
| ATR, volatility, support/resistance, авто-SL/TP предложение | Не добавлять в этой задаче | Риск считаем от ручного stop-loss, а не от тех-индикаторов |
